# Loom Image Blend And Compress Workflow Art Design

## Objective

Create an installable Loom Art named `图片融合并压缩` whose execution type is
`workflow`. The Art must accept two required image inputs, blend them through
the existing script Art, compress the blended result through the existing CLI
wrapper Art, and return the compressed image.

This Art is the real-world acceptance case for Loom's workflow framework. A
successful implementation proves that a workflow Art can bind multiple root
inputs, pass optional parameters to child Arts, execute child Arts in dependency
order, transfer an image result between children, and return the terminal image
through Hook Bridge `art/process`.

## Existing Components

The workflow must reuse these installed Arts instead of duplicating their
implementations:

- Image blend Art: `custom-image-blend-script`
  - Framework: `script`
  - Primary image input: `input`
  - Reference image input: `reference`
  - Blend parameter: `mix_ratio`, range `0..100`, default `50`
- Image compression Art: `custom-1770146354922`
  - Framework: `cli_wrapper`
  - Compression level: `level_num`, range `1..4`
  - Quality parameter: `quality_num`, range `60..100`
  - Lossless flag: `lossless`

The `workflow` framework is built into Loom and is already installed and ready.

## Identifiers

- Workflow ID: `image-blend-compress-workflow`
- Art ID: `custom-image-blend-compress-workflow`
- Display name: `图片融合并压缩`
- Framework dependency: `workflow`
- Child Art dependencies:
  - `custom-image-blend-script`
  - `custom-1770146354922`

These identifiers are stable so saved Hook nodes and installed packages can be
restored across restarts and future Art upgrades.

## Public Interface

### Required image inputs

| Label | ID | Type | Runtime role |
| --- | --- | --- | --- |
| 图片 A | `input` | image | Primary AHRP image and blend source |
| 图片 B | `reference` | image | Auxiliary AHRP image and blend reference |

Hook sends `input` as the normal `art/process` input and sends `reference`
under `input_images.reference`.

### Optional parameters

| Label | ID | Range | Default | Child target |
| --- | --- | --- | --- | --- |
| 融合值 | `mix_ratio` | `0..100` | `50` | `blend.mix_ratio` |
| 压缩比例 | `quality_num` | `60..100` | `90` | `compress.quality_num` |

The accepted compression semantics are option A: `压缩比例` maps directly to
Pingo's existing `quality_num`. Lower values produce stronger lossy compression
and lower visual quality.

The workflow keeps the remaining compression settings internal:

- `level_num = 2`
- `lossless = false`

## Workflow Graph

The repository-owned workflow definition is stored at:

```text
resources/workflow-arts/image-blend-compress/workflow.yaml
```

Its graph is:

```text
input + reference -> blend -> compress -> final image
```

The declarative YAML is:

```yaml
name: 图片融合并压缩
nodes:
  - id: blend
    uses: custom-image-blend-script
    with:
      mix_ratio: 50

  - id: compress
    uses: custom-1770146354922
    needs:
      - blend
    with:
      input: ${{ nodes.blend.outputs.output_base64 }}
      level_num: 2
      quality_num: 90
      lossless: false
```

The explicit image reference on `compress.input` makes the data flow
independent of incidental node ordering. The `needs` dependency enforces that
compression cannot start until blending succeeds.

## Workflow Bindings

The workflow Art manifest uses `execution.type = workflow` with these bindings:

| Workflow argument | Node | Target | Kind | Reason |
| --- | --- | --- | --- | --- |
| `input` | `blend` | `input` | `input_image` | Sets the child tool's primary image |
| `reference` | `blend` | `reference` | `param` | Preserves the second image as a named child argument |
| `mix_ratio` | `blend` | `mix_ratio` | `param` | Overrides the YAML default when supplied |
| `quality_num` | `compress` | `quality_num` | `param` | Overrides the YAML default when supplied |

The primary output binding selects the complete result of the `compress` node:

```json
{
  "nodeId": "compress",
  "output": "output_base64",
  "kind": "node_result"
}
```

Selecting `node_result` preserves the image content response generated by the
CLI wrapper instead of converting it into text or returning the intermediate
blend result.

## Package And Installation

Add a dedicated installer:

```text
scripts/Install-LoomImageBlendCompressWorkflowArt.ps1
```

The installer must:

1. Read the repository workflow YAML.
2. Build a package containing `manifest.json` and the workflow YAML.
3. Declare `metadata.dependencies.framework = workflow`.
4. Declare both child Art IDs in `metadata.dependencies.arts`.
5. Verify the workflow framework is installed and ready.
6. Verify both child Arts are present before local installation.
7. Save the workflow under `image-blend-compress-workflow`.
8. Install or replace the workflow Art under the Loom control plane.
9. Update `tools/tools.json` without changing unrelated tools.
10. Broadcast the Art-list update to connected Hook clients.
11. Support package-only and local install modes consistent with the existing
    image blend and image compression installers.

The installed Art remains a workflow Art. The installer must not rewrite it as
a script or CLI wrapper.

## Runtime And Error Behavior

- Hook must treat both declared image ports as required execution inputs.
- Missing 图片 A or 图片 B prevents automatic execution and identifies the
  missing port.
- Direct AHRP calls that omit a required image return a workflow execution
  error rather than an empty or pass-through image.
- A blend failure stops the workflow before compression.
- A compression failure returns the compression error and does not return the
  intermediate blend image as success.
- A successful execution returns only the compressed terminal image.
- Hook and Loom browser views continue to use the existing synchronized
  success/error events and error-detail rendering.

## Test Strategy

Implementation follows red-green-refactor.

### Workflow runtime tests

Add focused tests proving:

- two root image arguments can bind to one child as primary and named images;
- scalar bindings override YAML defaults;
- the blend node runs before the compression node;
- an image result reference becomes the compression child's primary input;
- the configured terminal node is returned;
- a missing required auxiliary image fails clearly;
- child execution errors propagate without returning an earlier image.

### Daemon and Hook Bridge tests

Add an `art/process` integration test with:

- two valid PNG inputs;
- an explicit `mix_ratio`;
- an explicit `quality_num`;
- the real workflow execution route;
- a decoded final image assertion.

The integration test must confirm that the returned image dimensions match the
blend output and that a known source/reference pixel produces the expected
blend before compression.

### Installer contract tests

Verify that the installer and generated manifest contain:

- the stable workflow and Art IDs;
- `execution.type = workflow`;
- all four workflow bindings;
- both child Art dependencies;
- the fixed compression settings;
- the terminal output binding.

### Live acceptance

Install the Art into the active local Loom control plane and issue a real Hook
Bridge WebSocket `art/process` request. Decode the returned image and record:

- response status;
- elapsed time;
- output dimensions;
- representative output pixel;
- output byte length.

Then confirm the Art appears in Hook with two image ports and two editable
optional parameters.

## Non-Goals

- Do not reimplement image blending inside the workflow Art.
- Do not reimplement Pingo compression inside the workflow Art.
- Do not add a generic workflow expression language or parameter transforms.
- Do not expose `level_num` or `lossless` in this acceptance Art.
- Do not modify the existing child Art IDs or their public contracts.
- Do not require Hook-specific hard-coded handling for this Art ID.

## Acceptance Criteria

The workflow framework is considered initially accepted when all of the
following are true:

1. The Art is installed and reported as `execution.type = workflow`.
2. Hook renders 图片 A and 图片 B as required image inputs.
3. Hook renders 融合值 and 压缩比例 as editable numeric parameters.
4. A real request executes the image blend child first.
5. The blend result is passed to the image compression child.
6. The returned image is the compression child result.
7. Missing inputs and child errors are surfaced as execution failures.
8. Automated runtime, daemon, installer, and formatting checks pass.
9. A new Loom release is produced in the required release directory.
