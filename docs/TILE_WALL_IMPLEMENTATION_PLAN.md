# 可交互瓷砖与虚拟屏幕实施计划

状态：实施中。本文是 Hook issue #25 在 Loom、Hook 两个独立仓库中的任务清单和验收记录。

需求来源：[Hook #25](https://github.com/aiaimimi0920/Hook/issues/25)、
[公开讨论](https://chatgpt.com/share/6aa1791f-86a8-83ee-b7c3-6f9ff09d5416)，以及本次开发对话中用户对物理瓷砖、无头中控和双向交互的明确说明。

## 1. 必须保持的目标

瓷砖是物理显示与交互终端，拥有网络身份、显示输出和输入能力。当前用电脑与屏幕模拟终端，未来专用硬件通过相同的公开协议接入。应用面板、Hook Unit、Live 会话和 Art 内容是显示对象，与物理瓷砖分别建模。

Loom 可以无头运行；管理界面可以只运行在普通电脑。关闭管理界面不应停止显示或交互。每块瓷砖可以独立工作，也可以加入一面逻辑墙；允许多面墙、逐块扩展、移除和重新排列。

同一内容可以跨越屏幕接缝，或在多个位置显示。移动显示位置不应重复启动源程序、采集任务或 Art 执行。点击、拖动、滚轮和键盘经过 Loom 授权与路由，回到对应源程序或 Art。内容位置变化、终端断线和中控重启后需要明确恢复行为。

终端不能被假定拥有通用 CPU、GPU 或完整应用运行环境。能力协商描述其实际支持的画面传输、解码、渲染和输入。专用硬件的电源、电路与生产制造不在本次软件交付范围；当前终端必须用真实电脑与屏幕完成验收。

## 3. 所有权与数据边界

| 对象 | 所有者 | 内容 |
| --- | --- | --- |
| Tile endpoint | Hook 终端实现；Loom 保存注册信息 | 设备身份、稳定输出 ID、实际像素尺寸、显示和输入能力、在线状态 |
| Wall layout | Loom | 瓷砖位置、朝向、墙面范围、版本、成员关系 |
| Content placement | Loom | 独立内容 ID、来源引用、墙面位置、源裁剪区域、层级、交互策略 |
| Source session | 现有 Live / Surface / 资源 owner | 实际采集、程序状态、Art 实例；布局只引用它 |
| Presentation | Hook / 将来适配终端 | 选定物理屏幕上的显示、解码、资源生命周期 |
| Input authority | Loom | 焦点、操作租约、指针身份、可靠边沿、取消与回源路由 |
| Management | Loom desktop / 已认证 API | 注册、排列、内容放置、诊断和恢复操作 |

新增 `loom.wall.v1` 合同描述终端、墙面和映射，复用已有 Live / Surface 来源合同。不得把墙面假扮为一个 Live source，也不得给终端发送管理员凭证、源程序路径或私有 GPU 句柄。

墙面使用独立的逻辑坐标；终端输入使用该显示输出的物理像素坐标。系统执行终端像素到墙面、墙面到内容源的变换。所有变换必须使用同一布局版本，拒绝非有限数、零尺寸、超界和过期版本。内容矩形采用半开区间，接缝命中只有一个确定归属。

终端能力与可用性分离：注册能力不能自动授权操作，也不能证明端到端帧率。网络媒体、Surface 状态、Art 预览/正式输出和持久化布局各自保留边界。
